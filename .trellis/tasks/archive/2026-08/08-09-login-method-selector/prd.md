# 登录方式选择与账号密码前端预留

## Goal

把 `/login` 从单一按钮区域重构为清晰的登录方式选择界面。微信和 Telegram 继续使用现有的真实渠道认证；账号密码仅提供诚实的前端预留，不创建后端凭据、不发送密码请求，也不伪造登录成功。

## Background

- 当前 `LoginPage` 已支持微信和 Telegram challenge：创建指令、轮询批准状态、交换 Session Cookie 并跳转资料库。
- 当前登录方式完全依赖 `/api/v1/capabilities`。能力接口加载失败时，页面隐藏所有入口，只显示“重试”。
- 后端没有用户名、密码哈希、注册、重置密码或密码登录 API；现有用户归属仍以可信渠道身份为准。
- 用户已确认：账号密码登录目前只要求前端存在，主要登录方式仍是微信和 Telegram。

## Requirements

1. 登录页默认展示三个方式条目，顺序为微信、Telegram、账号密码；前两个条目必须在视觉和文案上标明为主要方式。
2. 微信和 Telegram 条目必须始终可见：
   - 能力加载中时显示“正在检测”并禁用；
   - 服务端声明启用时可以点击并创建对应 challenge；
   - 服务端声明未启用时显示“当前部署未启用”并禁用；
   - 能力接口失败时显示“暂时无法连接”并禁用，同时提供重试入口。
3. 点击可用渠道后沿用现有真实流程：显示发送指令、等待批准、成功交换 Session Cookie，并自动跳转 `/library`。
4. challenge 创建中、等待批准、确认成功、失败和重新获取必须有互斥且可理解的状态文案。
5. 账号密码条目标明“前端预留”，点击后打开账号和密码表单：
   - 使用原生、可访问的表单标签；
   - 支持显示或隐藏密码；
   - 空字段提交时给出本地校验错误；
   - 非空提交时明确显示“当前版本暂未接入账号密码认证，请使用微信或 Telegram”；
   - 不调用任何网络接口，不写入 Web Storage，不跳转资料库。
6. 所有登录方式、错误、加载和帮助文案在桌面与 390×844 手机视口中均可阅读、可键盘操作且没有横向溢出。
7. 保持现有同源、CSRF、HttpOnly Session Cookie、浏览器 challenge secret 仅存内存及私有缓存清理边界不变。

## Acceptance Criteria

- [x] 能力接口 pending、error、单渠道启用和双渠道启用四种情况下，三个登录条目都存在，渠道条目的可用状态与服务端事实一致。
- [x] 点击启用的微信或 Telegram 会向 `createChallenge` 传入正确渠道，并进入真实 challenge 界面。
- [x] challenge approved 后仍交换 Session、调用 `onAuthenticated` 并进入资料库。
- [x] 账号密码表单包含账号、密码、显示密码和返回方式列表控件；空值与非空提交分别显示准确状态。
- [x] 账号密码提交不会调用 challenge、Session 或任何新 API，也不会在 `localStorage` / `sessionStorage` 写入数据。
- [x] 所有新增控件具备可访问名称，错误使用 `role="alert"` 或等价实时反馈。
- [x] 前端测试、类型检查、lint、生产构建和 OpenAPI stale check 全部通过。
- [x] 真实浏览器桌面和 390×844 手机端无横向溢出、无前端未捕获运行时错误；仅启动 Vite 而未连接后端时，capabilities 请求的 502 会被页面明确降级显示。

## Out of Scope

- 后端账号密码认证、密码哈希或凭据表。
- 自助注册、邮箱/手机号验证、找回密码、重置密码和账户锁定。
- 微信或 Telegram OAuth 跳转；现阶段继续使用已有聊天渠道 challenge。
- 修改用户归属、渠道绑定、Session Cookie 或 CSRF 契约。

## Risks and Deferred Items

- 账号密码入口必须明确标记为未接入，避免用户误以为已有可用账户体系。
- 如果未来实现真实账号密码认证，需要单独评审账号来源、凭据绑定、慢哈希、限流、锁定、找回流程和重复用户归属。
